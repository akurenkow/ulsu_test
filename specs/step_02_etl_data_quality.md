# Этап 2. ETL и Data Quality (Вопрос 1)

## Цель этапа

Реализовать регулярный пакетный ETL-пайплайн, который извлекает данные из операционного источника `deals_bigdata`, валидирует и очищает их, конвертирует валюты в RUB, обогащает категории и **идемпотентно** загружает результат в базовый слой хранилища (`core` DWH). Отбракованные строки не теряются: фиксируются в карантине/логах.

## Задачи этапа

### 2.1 Проектирование Core DWH

- Создать DDL слоя `core` (схема `core`) в `sql/dwh/`:
  - `core.prices` — очищенные сделки с нормализованной ценой `price_rub`, заполненными категориями;
  - справочники `core.cities` (дедуплицированный — этап 3, но структуру заложить), `core.body_types`, `core.body_groups`, `core.exchange_rates`;
  - карантин `core.dq_quarantine_prices` (или `dq_quarantine_prices`).
- Определить `raw` → `core` переход: raw-слой опционален, но исходник не должен модифицироваться.

### 2.2 Валидация и очистка (Data Quality & Cleansing)

Отфильтровать невалидные записи и отправить их в карантин с кодом причины:

| Правило | Код причины |
| :--- | :--- |
| `price <= 0` | `INVALID_PRICE` |
| `price <= 1000` **для RUB** (`currency_code = '643'`, source-validation диапазон) | `PRICE_BELOW_SOURCE_RANGE` |
| `distance <= 0` | `INVALID_DISTANCE` |
| `total_weight < 0` | `INVALID_WEIGHT` |
| `total_volume < 0` | `INVALID_VOLUME` |
| город `loading_city_gcid`/`unloading_city_gcid` отсутствует в `cities` | `MISSING_CITY` |
| валюта 840/978 без точного курса по `nearest_rate_date` | `MISSING_RATE` |

Важные уточнения из задания:

- Совпадение `loading_city_gcid = unloading_city_gcid` **не является** обязательным DQ-правилом. Исходный job сохраняет такую пару и расстояние; отбраковка допустима только как отдельно документированная бизнес-гипотеза.
- Структура карантина: `price_id`, `reason_code`, `raw_price`, `currency_code`, `nearest_rate_date`, детали строки, `detected_at`, `batch_id`. Логировать агрегатную статистику отсева по каждому коду.

### 2.3 Конвертация валют в RUB

- Источник: `currency_code` = `643` (RUB), `840` (USD), `978` (EUR).
- Для RUB `price_rub = price` (курс 1.0).
- Для 840/978 используется **точный курс по `nearest_rate_date`** (`exchange_rates.setting_date = nearest_rate_date`).
- Если точного курса на `nearest_rate_date` нет (например, выходной, или `nearest_rate_date IS NULL`) — строка **исключается из нормализованной витрины** и уходит в карантин (`MISSING_RATE`). **Fallback по `loading_date` не требуется.**
- Учесть нюанс из `data-requirements.md`: в production `nearest_rate_date` заполняется относительно `created_at` (последний `setting_date <= created_at`, а если курса ещё нет — последующий). Для детерминированности в решении для редкой будущей ветки использовать `MIN(setting_date) > created_at`. Зафиксировать выбранную логику в README.

### 2.4 Обогащение категорий

- **`weight_category`** (заполнять пропуски по `total_weight` с округлением до `0.1` т):
  - `G20T` — `>= 30.0`;
  - `FTL` — `[10.0; 30.0)`;
  - `10T` — `[5.0; 10.0)`;
  - `5T` — `[2.5; 5.0)`;
  - `L5T` — `[0.5; 2.5)`;
  - иначе `OTH`.
- **`volume_category`**: `FTL` при `0 < total_volume <= 120`, иначе `OTH`.
- **`outlier_mark`** — использовать как входной флаг: записи с `outlier_mark = true` исключаются из рыночной витрины (реализуется на этапе 3), сам флаг в базовом решении **не пересчитывается**.
- **Краевой случай (зафиксировать в README):** самые свежие сделки за день снимка `2026-10-26` ещё не прошли ночной job разметки аномалий и имеют `outlier_mark = false` по умолчанию — это ограничение исходных данных.
- **Опционально (★, не обязательно):** дополнительный пересчёт выбросов по аналогии с `MarkOutlierPrices`: только факты, группа `price_group_id` с минимум 4 строками, IQR по сырому `price`, P5–P95 по сырому `price_km`. Если реализуется — зафиксировать точную логику; это не замена фильтра `outlier_mark`.

### 2.5 Идемпотентность и Backfill

- Пайплайн параметризуется окном дат `start_date` / `end_date` (или `logical_date` в Airflow).
- Повторный запуск за уже загруженный период **строго идемпотентен**: число строк и суммы/перцентили не задваиваются.
- Реализация: `UPSERT / ON CONFLICT` (по естественному ключу `price_id` + дате загрузки) либо атомарная перезапись `DELETE + INSERT` в одной транзакции. Дедупликация в ClickHouse — вариант для бонуса.
- Обеспечить очистку карантина при повторном прогоне того же батча (не копить дубли причин).

### 2.6 Производительность и батчинг

- Пакетные операции через `execute_values` / `COPY` / векторизованную вставку / SQL `ELT`.
- **Запрещены** построчные `INSERT` в Python-цикле на сотнях тысяч записей.
- Чтение источника — потоковое/батчами, без загрузки всех 300k строк в память без необходимости.

### 2.7 Логирование

- Фиксировать: сколько строк прочитано, сколько отсеяно по каждому DQ-коду, сколько загружено/обновлено в `core.prices`, сколько в карантине.

## Критерии приёмки

- [ ] Все заложенные в `synthetic.sql` краевые случаи корректно обрабатываются (нулевые/отрицательные цены, `price <= 1000` для RUB, валюта без курса, битые города и т. д.).
- [ ] Строки с валютой без точного курса не попадают в нормализованную витрину и есть в карантине.
- [ ] `weight_category`/`volume_category` заполнены корректно, включая границы (`10.0`, `30.0`, `0`, `120`).
- [ ] Двойной запуск за один период даёт идентичные количества строк и контрольные суммы/перцентили.
- [ ] Нет построчных `INSERT` в цикле.

## Интеграция с бонусной инфраструктурой (★)

Бонусная инфраструктура (Airflow/Superset/ClickHouse) уже создана на шаге 1.1 —
см. [`docker-compose.yml`](../docker-compose.yml), [`dags/etl_dwh_ml.py`](../dags/etl_dwh_ml.py),
[`sql/clickhouse/00_schema.sql`](../sql/clickhouse/00_schema.sql). В рамках этого этапа
замыкается только ETL-часть бонусного контура:

- **Airflow (`etl`):** DAG `etl_dwh_ml` уже вызывает
  `python -m etl.main --start-date "{{ ds }}" --end-date "{{ ds }}"`. Реализация
  `etl/main.py` в этом этапе **без изменения CLI** (`--start-date`/`--end-date`,
  `--batch-size`) автоматически становится стадией `etl` DAG. Менять `dags/` не нужно;
  идемпотентность повторного прогона за тот же интервал — уже требование этого этапа.
- **ClickHouse:** детальные/очищенные данные остаются в PostgreSQL (`core.prices`);
  в ClickHouse на этапе 3 переносятся только витрины `mart` (вариант A из бонусного ТЗ).
  На этом этапе структуру ClickHouse менять не требуется — DDL уже зафиксирован в
  [`sql/clickhouse/00_schema.sql`](../sql/clickhouse/00_schema.sql).
