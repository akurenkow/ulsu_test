## Задачи этапа

### 3.1 Справочники и устранение аномалий измерений

#### Дедупликация городов (`cities`)
- `gc_id` в источнике **не уникален** (Москва `1001`, Казань `1003` имеют по две строки с разными `full_name_local`).
- Для каждой цены использовать **одну** запись города: выбор строки с минимальным `cities.id` для данного `gc_id`.
- Прямой `JOIN` без дедупликации размножает сделки и искажает статистику — недопустимо.
- Материализовать дедуплицированный справочник (например, `core.cities_dedup`) и использовать его во всех витринах и в ML (этап 4).

#### Унификация групп кузова (`body_types` / `price_body_types`)
- У сделки может быть несколько дочерних `body_type` из 1С (`price_body_types`, многие-ко-многим), либо `body_type IS NULL`.
- Привести к стандартизированным бизнес-группам по `std_id`:

| Группа | `std_id` | Коды |
| :--- | :---: | :--- |
| Тент | `56` | 56, 57, 58, 59, 60, 61 |
| Рефрижератор | `4` | 4, 46, 47, 48 |
| Изотерм | `2` | 2 |
| Борт | `15` | 1, 15 |
| Прочие | — | остальные коды |
| Не указан | — | `NULL` |

- Порядок определения группы: `price_body_types` (по `std_id` родителя) → fallback на `prices.body_type` → «Не указан».
- **Не допускать дублирования одной цены внутри одной группы кузова** (одна цена = одна строка на группу; если у цены несколько совместимых дочерних типов, они схлопываются в одну строку группы).

### 3.2 Витрина «Карточка маршрута и коридор рыночных ставок»

#### Зерно (grain)
`месяц × город отправления × город назначения × группа кузова × весовая категория`.

- Месяц формируется из `price_dates.price_date` (долгосрочная заявка может попадать в несколько месяцев; использовать только `prices.loading_date` нельзя).
- `volume_category` сохраняется как атрибут, **не** добавляется в grain без явного обоснования.

#### Правила фильтрации выборки
- `is_fact = true` (`price_type IN (1, 2, 3, 4, 5, 9)`).
- `complex = false` (прямые маршруты).
- `price > 0`, `distance > 0`, корректно рассчитанный `price_rub`.
- Исключить `outlier_mark = true`.
- Исключить плановые месяцы из будущего: `price_dates.price_date > '2026-10-26'`.

#### Рассчитываемые метрики (в RUB без НДС)
- **Рыночный коридор за рейс (`руб./рейс`):** `p25_trip`, `median_trip`, `p75_trip`, `avg_trip` по `price_rub`.
- **Рыночный коридор за км (`руб./км`):** `p25_km`, `median_km`, `p75_km` по `price_rub / NULLIF(distance, 0)`.
- **Доказательная база (Data Trust):**
  - `trips_count` — число уникальных сделок в ячейке (`COUNT(DISTINCT price_id)`);
  - `carriers_count` — число уникальных перевозчиков (`COUNT(DISTINCT organization_id)` при `price_type IN (3, 9)`);
  - `cv_rate` — `stddev_samp(price_rub) / avg(price_rub)`; при < 2 наблюдений или нулевом среднем → `NULL`;
  - `mom_pct` / `yoy_pct` — относительное изменение `P50` к календарному предыдущему месяцу и к тому же месяцу прошлого года (в %); если ячейки нет или знаменатель равен нулю → `NULL`, **не** подставлять «последний доступный» месяц;
  - `reliability_level` — `HIGH` если `trips_count >= 30` **и** `carriers_count >= 5` **и** свежесть последнего месяца не более 30 дней относительно `as_of`; `MEDIUM` если `trips_count >= 10`; иначе `LOW_DATA`.

### 3.3 Физическая схема и обновление

- Схема `mart` с таблицами/материализованными представлениями: `mart_route_card` и/или `mart_market_corridor`.
- Выбрать стратегию обновления, гарантирующую идемпотентность: атомарная перезапись партиции месяца (`DELETE + INSERT` в транзакции) или `CREATE OR REPLACE MATERIALIZED VIEW` / refresh.
- Продумать индексы под фильтры BI (по маршруту, месяцу, группе кузова).
- Настроить пересчёт в общем конвейере после загрузки `core` (этап 2).

### 3.4 Эталонный SQL-запрос

- Оформить расчёт карточки маршрута как читаемый SQL (файл в `sql/dwh/`), который можно прогнать вручную для проверки витрины — это обязательный артефакт по чек-листу.

## Критерии приёмки

- [ ] Дубли `cities.gc_id` не размножают сделки (проверка на контрольной паре Москва/Казань).
- [ ] Одна цена не дублируется внутри одной группы кузова; `NULL` кузов попадает в «Не указан».
- [ ] Месяц витрины строится от `price_dates.price_date`; будущие месяцы после `2026-10-26` исключены.
- [ ] Метрики `P25/P50/P75`, `avg`, `cv_rate`, `mom_pct`, `yoy_pct`, `reliability_level` считаются по спецификации.
- [ ] Повторный пересчёт витрин не задваивает строки и не меняет перцентили.

## Интеграция с бонусной инфраструктурой (★)

Бонусная инфраструктура создана на шаге 1.1; на этом этапе она наполняется содержимым:

- **Airflow (`rebuild_marts`):** реализовать пересчёт витрин как вызов
  `python -m etl.main --rebuild-marts --as-of <DATE>` — CLI-флаг уже добавлен в каркас
  [`etl/main.py`](../etl/main.py), DAG `etl_dwh_ml` вызывает именно эту команду. Повторный
  пересчёт обязан быть идемпотентным (атомарная перезапись партиции месяца).
- **Apache Superset:** после появления витрин `mart_route_card` / `ml_price_predictions`
  настроить в UI датасеты поверх `dwh.mart` и демо-дашборд (медиана/квартили за рейс и за км,
  коридор P25–P50–P75, Data Trust, опционально «Факт vs Прогноз»), затем экспортировать:
  `superset export-dashboards --dashboard-ids <id> -f ../superset/dashboards/demo.zip`.
  Импорт и bootstrap — в [`superset/README.md`](../superset/README.md) и
  [`superset/superset-init.sh`](../superset/superset-init.sh).
- **ClickHouse:** наполнить [`clickhouse/loader.py`](../clickhouse/loader.py) переливкой
  `mart_route_card` PostgreSQL → `dwh.mart_route_card` ClickHouse (DDL уже в
  [`sql/clickhouse/00_schema.sql`](../sql/clickhouse/00_schema.sql)) батчами через
  `clickhouse-connect` (без построчных вставок) и `OPTIMIZE TABLE ... FINAL`; сверить
  число строк/контрольные суммы/перцентили с PostgreSQL. Зависимость `clickhouse-connect`
  — в [`requirements-clickhouse.txt`](../requirements-clickhouse.txt).
